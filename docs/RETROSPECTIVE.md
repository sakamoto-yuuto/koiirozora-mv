## 0.5 最值得带走的四点（你的总结，我补上细节）

### ① 歌词时刻靠人工打点，必须写进工作流
- 开源对齐模型（CTC 强制对齐、Whisper 系、歌声专用的 HubertFA / SOFA）都试过，做不到准确的逐字对应。v1 的自动对齐器行内偏差 0.5–2 秒。
- 你的方案：写一个程序把歌导进去，边听边敲键盘，每按一下记一个假名。349 个假名一次打完，成片里字幕和演唱几乎完全吻合。
- 流程见 5.3。工具只保留最少的操作：播放 / 暂停、记一个、撤销、退进几秒、点字重打。
- 自动模型的价值可以重新定位：拿你的打点当真值，评估模型到底准不准，而不是替代人工。

### ② 怎么调用 codex 生图（这部分你基本没插手，见 3.3 和 5.4）
- **提示词模板化**：每类素材一个模板（背景、由綺、冬弥、路人、物件、序列表），共同约束包括只用几种墨、不要渐变、绿幕、解剖约束、禁止文字、只拷贝自己返回的那张图。
- **参考图有顺序**：第一张是引导草图（构图、骨架）或要改的原图，接着是官方设定（只取身份信息），最后一张是风格锚点。提示词里写明「第几张图是什么、取它的什么」。
- **并发**：生图可以 10–16 路并发，每张约 2–3 分钟。
- **防错**：提示词文件用 LF 换行；拷贝失败时从 codex 的缓存目录找回；并发时可能拿错图，所以每张都核对内容。
- **审图 → 改提示词**：打回原因记进 `REVIEW.md`，下一版提示词就照着改。局部错误用改图任务修，不必整张重来。

### ③ 清楚自己能调用哪些 agent，各自适合什么

| 助手 | 适合做 | 本项目里做过的 |
|---|---|---|
| **dsh**（DeepSeek，可联网搜索，便宜） | 搜集资料，找图片和视频素材，考证官方设定，审稿 | R01 审分镜；R02 调研歌声对齐模型；R03 考证 TV 第 4 话「すれ違い」；冬弥官方参考图的来源考证 |
| **codex**（GPT，带 image_gen） | 生成图片；有明确验收标准的工程杂活：评估开源音频模型准不准、怎么改进，分析渲染为什么慢、怎么提速，写工具 | 全部生图；T01 音效合成；T02 / T12 对齐；T08 / T09 / T09b 渲染提速；T11 Blender 预演 |
| **Claude**（主力模型，额度最贵） | 导演判断、镜头设计和实现、审图把关、编排其他助手 | 12 段镜头、管线设计、审图、交接 |

要边用边总结每个模型的特点：
- dsh：搜得快、便宜，但结论要交叉核对（R03 就如实写了「没有找到完全对应的镜头」）。
- codex：生图稳定，但手和关节不可靠；写代码时要给它划定只能改哪些文件。
- Claude 自己：上下文和额度都有限，要留给只有我能做的判断。

### ④ 严格控制 agent 的数量和额度
- 那次事故：图片的手有明显错误（指节长度怪、多一只手、少一只手），我问你能不能派 agent 去看，然后一次派出约 50 个和我同型号的 Opus agent 去审，你的 token 一下子烧光。
- 错在两点：(a) 一次派太多；(b) 派之前不说要派什么配置。
- 规矩：
  - 派任何 agent 之前，先说清楚派几个、什么模型、做什么、预计多少消耗；
  - 同时最多一两个；
  - 审图这类重复劳动，优先交给便宜的模型或工具（例如先用脚本做初筛），主力模型只做最后的判断；
  - 主力模型的额度最宝贵：能外包的都外包，但不能外包「判断」。

| 阶段 | 做法 | 结果 |

| v1 | 我写导演方案和前奏；V1 以后的段落外包给 codex（T04–T07）；codex 和 dsh 跑满并发生图 | 每段单看都能跑，合起来叙事散、画风不统一、意象看不懂。你的评语是「后面得你亲力亲为」 |

| 事故 | 生成的图有明显的手部错误（指节长度怪、多一只手、少一只手）。我问你能不能派 agent 去审，然后一次派出约 50 个和我同型号的 Opus agent，事先没说用什么配置 | 你的 token 一下子烧光，你叫停。之后定下规矩：最多一两个帮手；派之前先说清楚要派几个、什么模型、做什么；主力模型的额度最宝贵，能外包给便宜模型的都外包 |

**经验**：
- 导演判断（这一镜在讲什么、观众能不能看懂）不能外包。外包只适合有明确验收标准的机械活：生一张图、写一个工具、提一次速。
- 一段一段做，一段一段确认，返工范围最小。
- agent 数量越多，越难审，也越容易失控。

## 3. 困难与解决方案

格式：**问题** → **方案**（标出是谁提的）→ **经验**。【你】= 用户，【我】= Claude，【codex】/【dsh】= 外包助手。

### 3.1 叙事与可读性

1. **第一版看不懂。** 全片反复出现留言机，还有 REMAINING UNITS、TAPE COUNTER 这类科技风 HUD 面板，你「都不太理解其含义」。另外「世界中」配屋顶、她在看什么、结尾房子放大，都莫名其妙。
   - 方案：【你】提出原则——每个画面不看文档也能看懂，不要 HUD。【我】重写 v2 剧本：只保留观众能直接读懂的东西（一条街、一座电话亭、她、他的背影、他的房间、记忆里的两个人）；读数只留在电话机自己的小 LED 上；留言机全片只在关键处出现。
   - 经验：「检验一个镜头：这是这通电话里的哪一刻？」要在动手前回答，而不是做完再解释。
2. **冬弥全程不出现，很奇怪。**
   - 方案：【你】至少给个背影。【我】定为「只露背影和局部（手、肩、后脑），永远不露脸」，严格按官方三视图生成。
3. **先弄清歌曲背景。** 你问这首歌到底是写给英二还是冬弥的。
   - 方案：【我】查原作第 24 话：由綺彩排时唱这首歌，前后两次给冬弥打电话留言，结论写进 `research/lore.md`，剧情以此为准。
   - 经验：同人作品先查清人物关系，再写剧本。
4. **路人大叔没有存在理由。** 你问「不知道的还以为是冬弥发福了」。
   - 方案：【我】删掉。凡是不能回答「这个人在这一刻为什么在这里」的元素，一律删。
5. **后半段单调。** 拿听筒的镜头太多，运镜全是慢推，几乎全是硬切。
   - 方案：【你】提出 TV 第 4 话「すれ違い」的擦肩而过，给了原片和剧情说明，并建议让 dsh 去查原作画面致敬。【dsh】R03 调研确认第 4 话有「冬弥从正在打电话的由綺身后走过」的镜头。【我】写 v2.2：从 C2 起两条线交叉剪辑（她往外走，他往家赶）；C2 L21 用片头同一机位，让他从她的电话亭前走过（致敬）；桥段剪辑一小节比一小节快；用匹配剪辑，例如霜里融开的洞接他家亮起的窗；最后在俯视的路口让两串脚印交叉。
   - 经验：用户对原作的记忆是很好的创意来源；把它落实成可执行的分镜（谁、在哪、哪一拍）是导演的工作。
6. **片尾重现第一句歌词，你问为什么。** 设计意图是「整首歌就是这段留言」，但当时只有渐弱的伴奏，字像凭空出现。
   - 方案：【我】给了两个选项，【你】选了让磁带真的放出她的声音：从人声分轨截出这一句，加小喇叭滤波和磁带抖动，字跟着声音出来。
   - 经验：抽象的结构点要用观众能感知的东西（声音、动作）兑现，否则就是只有作者懂的设计。

### 3.2 美术一致性（一个美术层）

1. **画风不统一。** v1 里代码画的小人和生成的由綺放在一起「太违和了」。
   - 方案：【你】路人也让 codex 生成同一画风。【我】定下「一个美术层」：人物、路人、背景都是 codex 生成的三墨版画，代码只负责光、雪、视差、镜头和字。之后代码画的屋顶、电线杆、脚印也都逐步换成生成素材（脚印最后一个换）。
2. **详略不当。** 生成的陌生人「比主角还精细」，像主角。
   - 方案：【你】路人要比主角简单。【我】提示词模板加入 EXTRA 段落：大块平涂、少褶皱、脸三四笔。
3. **冬弥画得不像。**
   - 方案：【你】严格按官方参考图。【我】TOUYA 模板逐项写明发型（后脑圆润、不要尖刺）、外套（纽扣、两个贴袋、深棕领里）、浅蓝帽衫、窄肩，并把官方三视图和后脑设定图作为参考图附上；审图时逐项对照。
4. **手画错（反复出现）。** 三只手、手套感、三个指节、比例错。
   - 方案：
     - 【你】逐张指出，并提出「拆元素 + 先画骨架示意图」。
     - 【我】审图时放大数手臂、手、指节（记进记忆）。
     - 【我】写 `tools/guide.py`：画姿势骨架、手指骨链、布局框，作为第一张参考图。
     - 【我】提示词里写死解剖约束：恰好两只手、五根手指。
   - 经验：生图模型在手和关节上最不可靠，要靠示意图约束加人工逐张审，不要指望一次生成就对。
5. **同一道具两张图不一样。** 两个镜头里的电话机不是同一台。
   - 方案：【你】「把电话当成一个元素」，拆开生成再拼。【我】一个道具只生成一份（电话面板 `obj_phone_panel`、留言机 `obj_machine_*`），手是独立元素；在源图上量出键位和 LED 的坐标（`src/scenes/props.js`），代码按坐标合成。
6. **合成后图层不对。** v1 结尾按按钮的手和机器不在同一图层；C2 里递卡的手太小、被挡住。
   - 方案：【我】所有元素按「源图上量好的 u、v 坐标 + 物理尺寸（厘米）」摆放（`plateAt`、`fit`）；递卡改成卡片先弹出，再切到她看卡的镜头。
7. **手上自带的按键很难做出按下的效果**（最后一处）。
   - 方案：【你】把按键去掉。【我】在按键多边形内只保留手指和指甲（颜色 + 形态学 + 最大连通域），手指直接按留言机自己的「再生」键，键被压下并保持按下。
8. **生成图本身的瑕疵。** 路口俯视图里有两根电线没接在电线杆上（我漏看了）。
   - 方案：【你】指出后，【我】改图（`run_edit.sh`）去掉这两根线。代码画的电线一律从素材里电线伸出画面的位置接出去，走向保持一致。

### 3.3 生图管线

| 问题 | 方案 | 经验 |
|---|---|---|
| 并发时 codex 可能拿错图（v1 出现过两次）；拷贝到目标路径会静默失败 | 【我】提示词要求「只拷贝你自己那次调用返回的图」；`tools/codex_gen.sh` 失败时从 `~/.codex/generated_images/<session>` 找回 | 每张图都要人工核对内容 |

| 多墨背景怎么跟随全片的颜色状态 | 【我】`tools/plate_art.py` 把每张图量化成「墨标签图」，每种墨对应一个调色盘角色，由 `src/engine/plates.js` 按当前调色盘重新上色；三墨人物分版印刷，可以错版 | 生成图 = 结构，颜色交给代码，于是同一张背景能用在夜、黄昏、回忆、清晨 |
| 绿色物件不能用绿幕抠（公用电话本身是绿的） | 【我】改用品红幕（`--magenta`） | |
| 动作序列表各帧位置不对齐 | 【我】`tools/slice_sheet.py`：先 FFT 粗配准再细调；走路循环按头顶对齐（`--anchor top`） | |
| 生成的走路帧一会直走一会斜走；腿偏短 | 【你】要全部正背面直走。【我】画引导草图重生成；腿短不重生成，代码在下摆处切开、把腿拉长 1.4 倍，只用于远景 | 能用代码修的比例问题不必重生成 |
| 审图记录分散 | 【我】`art_src/v2/REVIEW.md` 逐张记录通过 / 打回和原因；`ingest.py` 一条命令入库 | 打回原因就是下一版提示词的修改清单 |

### 3.4 动画与连续性

1. **路人倒着走。** 素材本来就朝左，代码又翻转了一次。
   - 方案：【我】去掉多余的翻转；走路速度由步幅推算，脚不打滑。
2. **大叔瞬移；冬弥走着走着停了。**
   - 方案：【我】位置由时间连续推出，速度和步幅一致。
3. **由綺走路是一帧反复播放；切镜头时又从头走同一段路。**
   - 方案：【我】用真正的四帧走路循环；位置按全片时间计算（`walkers(env)`：从某个时刻起走了多远），所以不管切到哪个机位，她都在同一个位置、同一个步态相位上（记进记忆）。
   - 经验：动画的状态（位置、相位）要由全片时间决定，不能挂在镜头上。
4. **人物比例怪、整体偏小。**
   - 方案：【我】腿部拉长，并按透视重新定尺寸（`size ∝ 1 / 距离`）。
5. **脚印。** 不贴鞋形、和雪地割裂、穿模穿过电话亭。
   - 方案：
     - 【你】近景脚印要贴鞋形，要专门生成脚印素材；并允许「用巧妙的方法逃避」，建议穿模的镜头干脆不出现脚印。
     - 【我】生成 12 个脚印元素：她的靴 / 他的皮鞋 × 左右 × 俯视 / 45 度 / 贴地，按步幅铺设；穿模的近景镜头去掉脚印；只在远景和俯视里保留。
   - 经验：难做又不影响叙事的东西，允许回避，是很重要的生产授权。
6. **电车透视错，冬弥是背影却正对站台。**
   - 方案：【你】指出视角问题，建议侧面。【我】换成正对对面站台的平视背景，电车停在近轨，冬弥改成背侧 3/4 向左走。

### 3.5 字幕与音画对齐

1. **字幕节奏和演唱对不上、缺字、和画面里的字重复。**
   - 方案：
     - 【你】要求字幕只有一套。
     - 【我】右侧竖排逐字；4 个主角字落在实物上（雾玻璃上的「恋色空」、灯箱「黄昏」、毛笔「寂」、纸签「恋色の空」），落在实物上时竖排里留空（`HERO_WORDS`）。
     - 【你】另外选了纯日文、不加中文。
2. **自动对齐不准。** v1 的对齐器（T02 / T02b，人声分离加按字分配）行内偏差 0.5–2 秒。
   - 方案：
     - 【你】先要求 codex 和 dsh 广泛调研、自己做实验，再由我验收。【codex】T12（CTC 强制对齐）和【dsh】R02（歌声专用模型）给出了结果：R02 用「到最近人声起音的距离」这个代理指标评测，HubertFA 中位误差 20 ms。
     - 【你】又提出更直接的办法：写一个程序，你边听边按，每按一下记一个假名。
     - 【我】第一版标注工具做复杂了（多声道同时播放），被你否掉；改成极简的 `tools/tap.html`：空格播放 / 暂停，J 记下一个假名，退格撤销，左右键退进 2 秒，点假名重打，保存到 `out/tap/manual_taps.json`。你打完全部 349 个假名，`tools/refine_taps.py` 写回 `data/lyrics_film.json`。
     - 我试过把短语起点自动吸附到人声起音，结果会吸到换气声上，放弃。
   - 结果：「字幕节奏对了」，一次通过。
   - 经验：
     - 349 个点、一个人一次打完，人工打点又快又准，还不需要验证。
     - 自动方法要有真值才能评估；用代理指标得到的「20 ms」不等于看起来对。
     - 给用户的工具越简单越好。
3. **字幕看不见。** 奶油色的字落在冬弥同色的外套上就没了。
   - 方案：【我】`printChar` 的做法是：先印一层错位的深色阴影版，再印深色描边，最后印奶油色字，放在任何底色上都看得清。片尾字幕也用同样的处理。

### 3.6 渲染：速度与确定性

| 问题 | 方案 | 结果 |
|---|---|---|
| 渲染太慢（你：「不能开多线程吗」） | 【codex】T08：网点场缓存成离屏画布，逐像素一致；【我】并行分段导出 | 提速 1.1–2 倍 |
| 系统 FFmpeg 的 NVENC 探测失败，静默回退到 CPU 编码 | 外部诊断报告；【codex】T09 默认用项目内置的 `ffmpeg-static`，明示回退；有界帧流水线 | NVENC 可用 |
| 浏览器到 Node 的帧传输是瓶颈 | 【codex】T09b：加 `bufferutil`；YUV 传输在本机不更快，默认关闭 | 吞吐 +20% |
| 多路并发时内存压力大，导出失败 | 【我】并发降到 2–3 路 | 稳定 |
| **每次都从头渲染** | 【你】「只渲染发生更改或新的一段，然后剪到一起」。【我】`tools/render_film.mjs`：按段切成不超过 16 秒的小片；用「代码闭包 + 素材」算指纹，没改的小片直接复用；无损拼接后再混音 | 审一段只要 1–3 分钟；全片重渲约 21 分钟（3 路） |
| 分段渲染后接缝处像素不一致 | 【我】查出两处跨帧缓存造成的不确定性（`blitField` 第一次直接画、之后用缓存位图；网点光的缓存），改成每次都走同一条路径 | 拼接无缝 |
| 渲染进度看不见 | 【你】要进度看板；v1 做了 `tools/dashboard.html` | 升级任务 T10 写好了，还没做 |

**经验**：
- 确定性是增量渲染的前提：同一个时刻的画面，不管从哪里开始渲染都必须逐像素一样。
- 「只审改动的那段」把迭代周期从十几分钟压到一两分钟，这是整个项目效率提升最大的一步。

### 3.7 音频

1. **画面缺小音效，但不能喧宾夺主。**
   - 方案：【你】提出需求。【codex】T01 写 `tools/make_sfx.py`：用代码合成 16 类音效（脚步、门、按键 DTMF、回铃音、继电器、磁带……）；每个音效的音量相对当时音乐的 RMS 定标；歌曲本身从不做增益；只对总和做软限幅。【我】每段写 `<段>Sfx(env)` 事件表。
2. **写标题时的擦玻璃声不明所以。**
   - 方案：【你】删掉。音效必须对应画面里看得见的动作。
3. **峰值。** 音效叠加后限幅前峰值偏高。
   - 方案：【我】逐个定位峰值来源（例如「再生」的继电器声），调低 `rel`。现在限幅前约 1.09，软限幅后 0.999。
4. **磁带人声。**
   - 方案：【我】从 Demucs 人声分轨截取，带通 380–3000 Hz，加 0.6 ms 抖动（磁带的走速不稳），再用简单的自动增益把波峰与均值之比从约 8 压到约 6，最后按峰值定音量（约 -18 dB，和渐弱的伴奏持平）。

## 5. 可复现的制作流程

下面是 v2 实际走通的流程，换一首歌也适用。

### 5.0 环境

- Node（`playwright-core` 无头 Chrome 渲染，`ffmpeg-static` 编码，支持 NVENC）。
- Python 虚拟环境：numpy、scipy、Pillow、librosa、soundfile；人声分离用 Demucs。
- 生图：codex CLI（内置 image_gen）。审稿和调研：dsh（DeepSeek，可联网搜索）。这两个都可以换成你手头的同类工具。

### 5.1 定方法（一次）

1. 找一个参考作品，拆它的方法，而不是复制它的画面。
2. 定一个**叙事装置**（这里是 1986 年的公用电话和留言机），回答：歌词在这个世界里是什么？（这里是她对着话筒说的话。）
3. 定**颜色＝状态**：每种颜色代表什么，只在发生了事的时候变。
4. 先把一段（前奏）做到最终质感，作为全片的视觉基准（`docs/VISUAL.md`）。

### 5.2 考据与剧本

1. 查作品和歌曲背景、年代道具（`research/lore.md`、`research/phone1986.md`）。
2. 写分镜，每一镜写「这是这通电话里的哪一刻」。
3. 交给外部审稿（dsh），逐条取舍；分镜修订按版本写在文件顶部（v2 → v2.1 → v2.2）。
4. 硬性规矩写成清单：例如「不露脸」「只有一套字幕」「不要 HUD」。

### 5.3 歌词时刻（人工）

```bash
.venv/Scripts/python tools/tap_prep.py     # 歌词 -> data/tap_data.json（逐假名）
node export/server.mjs                     # 打开 /tools/tap.html：空格播放/暂停，J 记一个假名，退格撤销
.venv/Scripts/python tools/refine_taps.py  # out/tap/manual_taps.json -> data/lyrics_film.json
node tools/beatmap.mjs 0 396               # 小节线、拍、每个字的时刻
```

### 5.4 美术管线

1. **提示词模板**（`art_src/v2/make_jobs.py`）：背景 BG、由綺 YUKI、冬弥 TOUYA、路人 EXTRA、物件 PLAIN、序列表 SHEET。共同约束包括：只用几种墨、不要渐变、绿幕、解剖约束、禁止文字。提示词文件必须是 LF 换行。
2. **引导草图**（`tools/guide.py`）：凡是姿势、手、元素之间要配合的，先画骨架和布局框，作为第一张参考图。
3. **生成**：`art_src/v2/run.sh <name>`；改图用 `run_edit.sh <name> <src>`。
4. **审图**：放大数手、手臂、关节；人物逐项对照官方设定；路人是否比主角简单；同一道具是否和已有元素一致。结论记进 `REVIEW.md`。
5. **入库**：`.venv/Scripts/python art_src/v2/ingest.py <name>`。三墨人物进 `assets/art`，可以错版；背景和多墨物件转成墨标签图进 `assets/plates`，按调色盘重新上色；序列表切帧对齐；物件组拆成单件。
6. **量坐标**：在源图上量出要对位的点（键位、窗户、门、电线出口……），以 0–1 的 u、v 写进代码常量。

### 5.5 一段一段做（核心循环）

```text
读：这一段在电话里发生什么、颜色状态、前后镜头怎么接（docs/PROCESS.md）
→ 节拍表：node tools/beatmap.mjs <from> <to>，每一拍写上「这一刻发生什么」
→ 镜头表：id、at（只落在拍或小节线上）、moment、layout、镜头运动
→ 实现：src/scenes/NN_xxx.js（fig / fit / backdrop / plateAt 合成元素，代码只做光、雪、视差、镜头和字）
→ 缩图审片：tools/sheet.sh <名字> <时间,...>，放大检查手、穿模、图层、走路方向
→ 音效事件表：<段>Sfx(env) → node tools/sfx.mjs && .venv/Scripts/python tools/make_sfx.py
→ 只渲染这一段：node tools/render_film.mjs --start S --end E --jobs 2 --out out/<段>.mp4
→ 交给用户审，按意见修，直到「可以，继续做 X」
```

**每段交付前的自检**：
- 每个画面不看文档能看懂吗？
- 这个人、这个东西为什么在这里？
- 走路的位置和相位跨镜头连续吗？
- 字有没有和画面里的字重复？
- 手数对吗？

### 5.6 全片

```bash
node tools/render_film.mjs --start 0 --end 395.41 --jobs 3 --out out/全片_720p.mp4 --dry   # 先看哪些小片会复用
node tools/render_film.mjs --start 0 --end 395.41 --jobs 3 --out out/全片_720p.mp4
```

改了 `kit.js`、`shot.js`、`index.js`、`stage.js` 这类共用代码，会导致所有段都重渲。

### 5.7 协作规矩（可以直接抄）

- 导演判断不外包；外包任务写成任务书（输入、输出、验收标准、可以改哪些文件），结果写回 `docs/tasks/Txx.result.md`。
- 同时最多一两个帮手；派之前先告诉用户派几个、什么模型、做什么。生图可以并发，但每张都要审。
- 按特长分工：dsh 搜资料、找素材、考证、审稿；codex 生图和工程杂活；主力模型只做判断和编排，它的额度最宝贵。
- 交接文档随时可用：进度、规矩、工具、坑、下一步。
- 速度优先：看不出差别的不抠，难做又不影响叙事的允许回避。

### 6.2 仓库整理和脱敏
- 为这个项目单独建了干净的仓库，不再用原来混着很多项目的工作目录。
- 排除：渲染输出、`node_modules`、所有虚拟环境、对齐实验的模型和缓存（约 16 GB）、生图日志（`*.log`、`*.msg`）、外包任务日志（`*.log`、`*.err`）、打回的废图。
- 脱敏：本机路径和 Windows 用户名替换成占位符或相对路径；生图脚本改成按脚本所在位置推算项目根目录；提交使用 GitHub 的 noreply 邮箱。密钥扫描只命中虚拟环境里第三方库的示例代码，这些目录已经排除。
- 以后要复用：克隆公开仓库，把私有仓库里的音频和歌词拷到同样的位置，按 README 安装依赖即可。

### 6.3 建议附带的「学习材料」

- 本文、`docs/PROCESS.md`、`docs/VISUAL.md`、`docs/STORYBOARD_v2.md`（剧本演变）、`art_src/v2/REVIEW.md`（每张图为什么通过或打回）、`docs/tasks/`（外包任务书和结果）。
- 一组「问题 → 修改后」的对比截图：手、冬弥、脚印、电车透视、字幕描边。这对学习的人最直观。
- 对话记录里有大量真实的审片意见，但包含个人用语；如果要公开，建议整理成摘录，而不是直接放原始记录。
