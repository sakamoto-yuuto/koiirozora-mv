# R02 逐字对齐：广泛调研 + 歌声专用 / Whisper 系实验

> 目标：给定 `assets/audio/track.mp3`（森川由綺「恋色空」，约 395 s）、Demucs 人声轨
> `assets/audio/vocals.wav`、26 行 LRC 时间和 `data/lyrics_kana.json` 的假名读音，
> 输出 349 个 mora 的起点。评测用 `tools/align_eval.py` 的**代理指标**（到最近人声
> onset 的距离），不是手工 ground truth；所有数字都是在这首歌上真实跑出来的。

## 0. 结论先行

| 结论 | 内容 |
|---|---|
| **首选** | **HubertFA Japanese ONNX v0.0.7**：349/349 mora，代理中位误差 **20.4 ms**，≤50 ms **73.9%**，≤100 ms **87.7%**，偏差 **+4.2 ms**，落在无声处 **1.1%**；CPU 每行约 1–3 s。 |
| **次选** | **SOFA Japanese v0.0.2**：中位 **50.9 ms**，≤50 ms **49.0%**，≤100 ms **76.8%**，偏差 **−32.2 ms**（系统性偏早）。加 32 ms 常数校准后中位 **37.5 ms**、≤50 ms **63.3%**、≤100 ms **80.5%**，但这只是代理指标上的校准，**没有参考标注不能算已验证**。 |
| **Whisper 系** | **stable-ts `align()` + Whisper large-v3** 能跑通，但中位 **109.0 ms**、≤50 ms **22.3%**、≤100 ms **46.4%**，比 baseline 还差。它给出字级时间，再按字符映射到 mora；通用语音模型 + 粗粒度 token 在唱歌上不够用。 |
| **基线** | `tools/align_lyrics.py` 的 DP：中位 **52.0 ms**、≤50 ms **48.4%**、≤100 ms **68.5%**、L25 **360.2 ms**。HubertFA 在 L25 上从 360 ms 降到 **26.8 ms**。 |

### 1.5 调研小结

- **日语歌声专用、可给定文本、phone 级**：真正成熟的只有 SOFA / HubertFA 这一支；LabelMakr 是它们的 GUI 包装。
- **卡拉 OK 工程化**：MiliKara / FA-Kara / nicokara-cloud 都把问题拆成“人声分离 + 注音 + CTC/MMS + LRC 锚点 + mora 映射”，成熟的是**流程**，不是某个新声学模型。
- **Whisper 系**：stable-ts 是唯一方便地“给定文本、词级/字级”且非 CTC 的现成实现；但它是语音模型，唱歌的连音/长音不是它的强项。
- **学术**：MIREX/DALI/Jiawen Huang 提供了数据和评价方法，但没有一个“日语 J-pop、开箱即用、phone/mora 级”的强基线；SingAlign 的普通话对比支持 HubertFA > SOFA。
- **平台逐字歌词**：YRC/QRC/TTML 是格式和编辑器生态，公开的自动生成器基本都回到 CTC/MMS/Whisper，没有“秘密成熟算法”可直接拿来。

## 2. 实验设置（三条路线共用）

### 2.1 输入与预处理

- 音频：`assets/audio/vocals.wav`（44.1 kHz 立体声，Demucs 人声；取单声道）。
- 行时间：`data/lyrics_film.json` 的 `start/end`，只作为**窗口锚点**，不把 `end` 当真理。
- 读音：`data/lyrics_kana.json`，用 `tools/align_lyrics.py` 的 `mora_units()` 切；全曲 **349 mora / 26 行**。
- 每行裁一段人声：左边界 `start − 0.4 s`；右边界
  `min(下一行 start − 0.03 s, 本行 end + 1.0 s)`。这样既不会把下一行的人声吞进来，也不会在
  L10→L11、L21→L22 这种长间奏处把整段伴奏交给模型（早期版本用“下一行 start”当右边界，
  L10 被拉进 30+ s 的间奏，L10/L21/L25 明显变差，已修）。
- 假名→音素：`tools/align_lab/common.py` 里的表，Hepburn 风格（`し→sh i`、`ち→ch i`、
  `つ→ts u`、`ふ→f u`、`じ→j i`、`を→w o`、`ん→N`、`っ→` 并入前一个 mora 或单独处理）。
  这首歌没有 `ー`，所以长音没有真正被考验。
- 输出：`out/align_lab/<method>.json`，26 行、349 mora、顺序和读音完全一致（`validate.py` 检查）。
- **数据版本**：实验期间 `data/lyrics_film.json` 被另一个 agent 在 **11:29:04** 修改过
  （L10 `end` 155.5→159.75，L19/L21 的 `end` 也变了；`start` 不变）。最终结果统一用这一版：
  stable-ts 在 11:44、HubertFA 在 11:48–11:50、SOFA 在 11:48–11:50 分别跑完。早期日志里
  L10=90.7 ms、HF L10=30.3 ms 等是旧 `end` 的中间结果，已作废；本报告表格全部是当前版本。
- 试听：`<method>_clicks.wav`，左声道原曲、右声道每个 mora 一声 22 ms / 1.8 kHz click。
- 看图：`<method>_L0.png`、`_L10.png`、`_L25.png`，人声频谱 + 每个 mora 的竖线 + 假名。

## 3. 实验 A：SOFA Japanese

### 做了什么

- 下载 `SOFA_model_JPN_Ver0.0.2_Beta.zip`（1.16 GB ckpt + `japanese-dictionary.txt` + `hparams.yaml`）。
- 每行裁人声、写 `.wav` + `.lab`（音素序列，`SP` 开头结尾，音素之间不插 `SP`）。
- `infer.py` 原样跑会失败：PyTorch ≥2.6 的 `torch.load(weights_only=True)` 拒绝这个 ckpt
  （`Unsupported global: GLOBAL getattr`）。`run.py` 在进程内复刻 `infer.py` 的流程，用
  `LitForcedAlignmentTask.load_from_checkpoint(..., weights_only=False)`。
- 还踩了 torchaudio 2.11 → torchcodec → FFmpeg DLL 的坑；最终降到 torch/torchaudio 2.5.1 CPU，
  `torchaudio.load` 原生可用。
- 解析 TextGrid 的 `phones` 层，按“每个 mora 的第一个 phone 起点”给 mora 时间；单独的 `っ`
  没 phone，暂用后一个 mora 的起点。

| L0 / L10 / L25 | 41.0 / 39.8 / 67.5 ms |

**看图**：`out/align_lab/sofa_jpn_L0.png`、`_L10.png`、`_L25.png`。
L0 上 SOFA 把最后的「を」放在 79.26 s；对照 codex 的 `reference_evidence/L00_detail_1.png`，
79.2–80.5 s 是一段持续的高音，79.26 作为「を」的起点是合理的，而 baseline 的 80.92 s 落在
持续音尾部/下一句前，明显偏晚。SOFA 在 L0 的 72 ms 主要是中间几个 mora 偏晚/偏早造成的。

**问题**：
- 系统性偏早约 34 ms（可能是 edge 模型把边界放在过渡的哪一侧），逐行都能看到。
- L10 / L21 / L25 的末尾 mora 仍不够稳：L10 在 158–159 s 的几个 mora 间隔偏大或偏小，
  L25 最后「ら」之后的长音只能靠 LRC `end` 兜底；说明模型在“长句 + 持续音”上仍有系统误差。
- 训练域是 JSUT + UTAU/歌声合成音源，不是商业 J-pop 女声；这次能跑到 50.9 ms 已经算可用，
  但不能保证换歌手/换曲风。

## 4. 实验 B：stable-ts `align()` + Whisper large-v3

### 做了什么

- 先按“调研首选”试了 `kotoba-whisper-v2.0-faster`（CT2，1.41 GB）+ faster-whisper 1.2.1 的
  `model.align()`。**没跑通**：在 `faster_whisper/transcribe.py:1709 self.model.align(...)`
  处 Windows `access violation`（0xC0000005），ctranslate2 4.8.3 / 4.5.0、`int8` / `float32`
  都复现；换 vanilla Whisper 才绕开。
- 下载 OpenAI `large-v3.pt`（2.94 GB），用 `stable_whisper.load_model(..., device='cpu')`。
- 每行裁人声（16 kHz），文本是**用空格分开的假名**（`た そ が れ …`），`language='ja'`，
  `nonspeech_skip=None`、`suppress_silence=True`、`max_word_dur=3.0`、`token_step=100`。
- stable-ts 对日语 `split_words_by_space=False`，所以它返回的是 token/字符级 word；脚本把
  `result.all_words()` 拼成字符串，用 `difflib.SequenceMatcher` 做单调字符映射，取每个 mora
  第一个字符的起点。
- 26 行连续跑时在第 18 行附近 native crash；`run.py` 改成每行写 `partial.json`，崩溃后
  `--start N` 续跑，最终合并 26 行。

### 结果

| 指标 | 值 |
|---|---:|
| mora 数 | 349 / 349 |
| 中位绝对误差 | **109.0 ms** |
| 偏差 | −11.7 ms |
| ≤50 ms | **22.3%** |
| ≤100 ms | **46.4%** |
| 落在无声处 | 0.0% |
| L0 / L10 / L25 中位 | **92.0 / 83.9 / 105.8 ms** |
| 推理时间 | 约 15–20 min（CPU，26 行；平均 30–45 s/行） |

**看图**：`out/align_lab/stable_ts_largev3_L0.png`、`_L10.png`、`_L25.png`。

**结论**：stable-ts 在这首歌上**明显不如 SOFA / HubertFA**，甚至不如 baseline（109.0 vs 52.0 ms，
≤100 ms 46.4% vs 68.5%）。原因不是“文本错了”，而是它给的是 Whisper 的 token/字级时间：
- Whisper 的 cross-attention 在唱歌的长音/连音上分辨率有限，常常把 2–3 个 mora 放进一个 token；
- 我们用 `difflib` 把字符映射到 mora，丢掉了 token 内部的细节；
- large-v3 是语音模型，训练目标不是“给定歌词的 phone 边界”。

这不是说 stable-ts 没价值：它可以做“整句/词级”字幕，或者作为**交叉检查**（如果它和歌声
对齐器差 >150 ms，基本可以判定该行有长音/转音/错词）。但作为逐 mora 主对齐器不推荐。

### 问题

- 通用语音模型，不是歌声模型；长音、melisma、连音处会把多个 mora 压到一个 token/一段里。
- CPU 很慢（约 30–45 s/行，全曲 15–20 min；还要分段续跑）。
- native crash 不是 Python 异常，不能 `try/except`；必须进程级分段。
- faster-whisper/kotoba 这条路本来更快、日语更强，但 CT2 `align` 在本机不可用；
  换一台 Linux/不同 CT2 版本的机器值得重试。

## 5. 实验 C：HubertFA Japanese（本次最佳）

### 做了什么

- 下载 HubertFA v0.0.7 ONNX（`model.onnx` 396 MB，自带 HuBERT 前端 + 日语词典
  `japanese_dict_full.txt` + `vocab.json`）。
- 每行裁人声（44.1 kHz），前面补 0.5 s 数字静音（给初始 `SP` 一个位置），写 `.wav`；
  `ph_seq = ['SP', 'ja/t', 'ja/a', ..., 'SP']`，每个 mora 是一个 word，`ph_idx_to_word_idx`
  把 phone 映射回 mora；不插 mora 之间的 `SP`。
- `InferenceOnnx` 直接跑（`onnxruntime` CPU），`pad_times=1`。注意：`pad_times=2` 时
  `find_all_duplicate_phonemes` 会因为两次 AP 插入不同而抛 “No duplicate groups”，所以用单次。
- 解析返回的 `Word` 列表，取每个 mora word 的 `start + crop_left`；单独 `っ` 用后一个 mora 的起点。

### 结果

| 指标 | 值 |
|---|---:|
| mora 数 | 349 / 349 |
| 中位绝对误差 | **20.4 ms** |
| 偏差 | **+4.2 ms** |
| ≤50 ms | **73.9%** |
| ≤100 ms | **87.7%** |
| 落在无声处 | **1.1%**（4 个 mora） |
| L0 / L10 / L25 中位 | **14.8 / 22.3 / 26.8 ms** |
| 推理时间 | 15–75 s（CPU；正常约 15 s，机器负载高时 37–75 s） |

**看图**：`out/align_lab/hubertfa_jpn_L0.png`、`_L10.png`、`_L25.png`。
- L0：14.8 ms。最后的「を」在 79.27 s，和 `reference_evidence/L00_detail_1.png` 里
  79.2 s 开始、持续到 80.5 s 的高音一致；baseline 的 80.92 s 是持续音尾部。
- L10：22.3 ms。前两个 mora 仍是 149.048 s（重复），但后段（158.2–159.3 s）跟上了修正后的
  LRC `end=159.75`；这一段正是 data 在 11:29 被另一个 agent 修正过的地方。
- L25：26.8 ms。13 个 mora 覆盖 320.1–330.4 s，最后「ら」从 330.4 s 持续到 334 s，
  baseline 的 360 ms 误差主要就是把持续音尾部当成起点。

**和 SOFA 的差异**：HubertFA 在 L0 的 75.53/75.65/75.87/76.04/76.24/76.64/77.04/77.43/
77.67/78.63/79.27 更贴近谱面上的能量/音高变化；SOFA 整体晚 0.1–0.3 s。两者在 L0 最后的
「を」上一致（79.26/79.27），说明分歧主要在中段连音，不是整行错位。

**问题**：
- L10 前两个 mora 重复；L21/L25 末尾仍可能偏早/受 LRC `end` 影响。
- 1.1% 落在无声处（4 个 mora），都在行边界附近。
- 没有可用的 per-mora 置信度（返回的 word 没有概率）；`conf` 字段一律省略，避免伪造。
- 模型权重没有写明确许可；训练数据/商用授权需要自行确认。

## 6. 数字对比

| 方法 | mora | 中位 | 偏差 | ≤50 ms | ≤100 ms | 无声处 | L0 | L10 | L25 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| baseline（`align_lyrics.py` DP） | 349 | 52.0 ms | +17.6 ms | 48.4% | 68.5% | 0.0% | 57.8 | 41.1 | 360.2 |
| SOFA Japanese v0.0.2（原样） | 349 | 50.9 ms | −32.2 ms | 49.0% | 76.8% | 0.0% | 72.3 | 30.7 | 94.7 |
| SOFA +32 ms（代理校准，诊断） | 349 | **37.5 ms** | −8.2 ms | **63.3%** | **80.5%** | 0.0% | 41.0 | 39.8 | 67.5 |
| **HubertFA Japanese ONNX v0.0.7** | 349 | **20.4 ms** | **+4.2 ms** | **73.9%** | **87.7%** | 1.1% | **14.8** | **22.3** | **26.8** |
| stable-ts + Whisper large-v3 | 349 | 109.0 ms | −11.7 ms | 22.3% | 46.4% | 0.0% | 92.0 | 83.9 | 105.8 |

（`sofa_jpn_cal` 是诊断用的常数校准，不是独立方法；不参与“最佳”结论。）

`baseline_current.json` 是 T12 的 eval 报告（不是对齐文件）；本表 baseline 的数字直接从
`data/lyrics_film.json` 的 morae 重算，和 `baseline_current.json` 完全一致（中位 52.0 ms、
≤100 ms 68.5%、L25 360.2 ms）。

**跨方法一致性**（逐 mora 绝对差）：

| 对比 | 逐 mora 绝对差中位 | 符号均值 | 落在 50 ms 内 |
|---|---:|---:|---:|
| HubertFA vs SOFA | 320.0 ms | −347.0 ms（HF 更早） | 10.3% |
| HubertFA vs stable-ts | 242.0 ms | −220.4 ms（HF 更早） | 4.3% |
| SOFA vs stable-ts | 134.0 ms | — | 25.8% |
| HubertFA vs baseline | 837.0 ms | −839.4 ms（HF 更早） | 9.2% |
| SOFA vs baseline | 607.0 ms | — | 10.9% |

这张表是本次最重要的“反面证据”：三个方法在代理指标上都不差，但彼此差很多。原因：
- 代理指标只找“最近的人声 onset”，而日语连续演唱里 200–300 ms 就有一个 onset；一个 mora
  错到相邻音节，仍可能落在 50–100 ms 内。
- 连音/转音（母音到母音）没有明显 onset，任何方法都只能靠模型先验；不同模型给出不同边界。
- 因此**不能只用 `align_eval.py` 的排名做最终验收**；T12 的手工 `reference.json` 是关键。

### 6.1 关于 `manual_refined.json`（不是 T12 的 reference）

实验期间 `out/align_lab/` 出现了另一个 agent 的 `manual_refined.json`（`method: manual_tap_refined`，
`source: out/tap/manual_taps.json`，349 morae，`moved: 311`，`moved_median_abs: 19 ms`）。
它不是 T12 任务要求的 `reference.json`，而且和谱面/代理指标**明显冲突**：

- 用它做 `--ref` 打分：HubertFA 中位 **377.2 ms**、SOFA **72.0 ms**、stable-ts **194.1 ms**、
  baseline **540.8 ms**；这和“HubertFA 最贴 onset、L0 最后「を」在 79.27 s 与持续音起点一致”
  的谱面证据不一致。
- 逐行看 L0：`manual_refined` 的 11 个点是
  `75.62, 75.97, 76.20, 76.33, 76.64, 77.04, 77.44, 77.65, 78.61, 79.01, 79.26`；
  HubertFA 是
  `75.53, 75.65, 75.87, 76.04, 76.24, 76.64, 77.04, 77.43, 77.67, 78.63, 79.27`。
  两者的“大跳”都发生在 77.6→78.6，但 `manual_refined` 在 79.01 多了一个点、把 78.61 之后
  的 mora 分配改了；这更像**人工点 note/vowel onset**，而不是“辅音起点”的 mora 边界。
- 因此本报告**不把 `manual_refined` 当 ground truth**，也不拿它的分数做推荐依据。若导演确认
  它才是标准答案，那么结论会反转成“SOFA 更接近人工”，但必须先把它的 mora 分配和
  “辅音起点 vs 母音起点”的定义对齐；这一步不能靠猜。

## 7. 推荐

### 7.1 直接可用

1. **HubertFA Japanese ONNX v0.0.7** 作为主对齐器：
   ```powershell
   tools\align_lab\hubertfa\.venv\Scripts\python.exe tools\align_lab\hubertfa\run.py
   ```
   输出 `out/align_lab/hubertfa_jpn.json` + clicks + L0/L10/L25 图。CPU 可跑，不需要 GPU；
   代理指标最好，L0/L25 和手工证据一致。**注意**：如果导演最终采信 `manual_refined` 的
   “note/vowel onset”定义，SOFA 的分数会反过来更好；这不是代理指标能裁决的，必须先统一
   “mora 起点 = 辅音起点还是母音起点”。
2. **SOFA Japanese** 作为第二意见：`sofa_jpn.json`。如果只看代理指标，它和 baseline 差不多
   （50.9 vs 52.0 ms），但它的**错误结构不同**（系统性偏早、连音处偏晚），可以作为
   “两个模型不一致就人工复核”的触发器。若要用于生产，先用手工参考确认 +32 ms 校准是否成立。
3. **stable-ts large-v3** 只建议做交叉检查/英文或说话段；不建议作为日语歌声主对齐器（慢、
   通用语音、崩溃风险）。

### 7.2 如果要更稳

- **LRC 行锚点 + 逐行裁窗**已经是必须的；不要整曲一次性喂给模型。
- **长间奏行**（L10/L21/L25）单独复核：LRC `end` 不可信，裁窗右边界用
  `min(next_start, end + 1.0)`，并把最后 1–3 个 mora 标成 `review`。
- **`っ` / `ー`**：`っ` 没有独立元音，当前用后一个 mora 的起点；`ー` 这首歌没有，换歌要专门处理
  （MiliKara 的做法：`ー` 与前一个音平分，遇到停顿最多延长 0.8 s）。
- **三方法中位数**：如果 reference 证明确实更稳，可以取 HubertFA/SOFA/stable-ts 的逐 mora 中位数
  作为保守值；但在没有 reference 前不建议直接上线。
- **换歌手/曲风**：SOFA 的训练域是 UTAU/JSUT，HubertFA 的日语训练域也未公开；商业 J-pop
  建议至少人工抽查 2–3 行（L0/L10/L25 这种有长音/长间奏的）。

## 8. 仍然不可靠 / 没跑通

- **没有 `reference.json`**：T12 的 codex 在 10:50 后日志停止（`memory allocation ... failed`），
  到本报告写完时 `out/align_lab/reference.json` 仍不存在。因此**没有 T12 `--ref` 分数**，所有数字
  都是代理指标；`out/align_lab/reference_evidence/` 只有图，没有 JSON。
- **`manual_refined.json` 不是 T12 reference**：它是另一个 agent 的 `manual_tap_refined`，
  用它打分和谱面/代理指标冲突（见 §6.1）；本报告没有拿它当 ground truth，也没有为了迎合它
  去改方法。
- **faster-whisper + kotoba-whisper CT2 `align()` 崩溃**：Windows access violation，
  ctranslate2 4.5.0/4.8.3、int8/float32 都复现；没有 kotoba 的数字。vanilla large-v3 能跑，
  但不是“日语专用模型”。
- **SOFA 原始 `infer.py` 跑不通**：PyTorch ≥2.6 `weights_only`；已在 `run.py` 里绕过。
  torchaudio 2.11 + torchcodec 的 DLL 问题也遇到过，最终固定 torch/torchaudio 2.5.1 CPU。
- **stable-ts 第一次连续 26 行 native crash**：第 18 行附近 0xC0000005；改成每行写
  `partial.json` 后，第二次完整跑完 26 行（未复现崩溃）。根因没找到（可能是 large-v3 CPU +
  长时累计内存/线程问题），但分段续跑是可靠的兜底。
- **代理指标本身**：连音、长音、melisma 会低估所有方法；也会奖励“错到相邻 onset”。
  `in_silence` 只能抓“落在静音”，抓不到“落在错误音节”。
- **SOFA 的 +32 ms**：是从本曲代理偏差直接读出来的，属于“在同一把尺子上校准”，
  不是独立验证；换歌/换录音可能不成立。
- **没有 GPU 数字**：本机 RTX 3050 4 GB，SOFA/HubertFA 都用 CPU；stable-ts 也是 CPU。
  GPU 上速度会不同，精度不应有本质变化，但没有实测。
- **没有跑**：MiliKara / FA-Kara / nicokara-cloud（CTC，和 T12 重复）、LabelMakr（GUI）、
  NNSVS/ENUNU（乐谱驱动）、UTAU oto（voicebank）、Jiawen Huang（无日语）。
  这些都在 §1 写了原因，没有编数字。
