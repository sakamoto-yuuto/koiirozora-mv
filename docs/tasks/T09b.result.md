# T09b 浏览器 → Node 帧传输结果

## 结论

瓶颈假设成立。1280×720 的 RGBA 帧为 3,686,400 bytes，而 YUV420 帧为
1,382,400 bytes（减少 62.5%）。在导出器完全相同的 headless Chrome、GPU
flags、WebSocket ACK 背压和 Node 接收端下，大帧确实受浏览器发送及 Node
解掩码影响。原接收端不是 `ws` 包，而是项目的自写实现；因此此前没有使用
`bufferutil`。

| 解掩码 | 帧大小 | 浏览器端 MB/s | Node 接收 MB/s |
| --- | ---: | ---: | ---: |
| JS（改动前路径） | 3.686 MB RGBA | 79.9 | 81.9 |
| `bufferutil` | 3.686 MB RGBA | 99.2 | 100.4 |
| JS（改动前路径） | 1.382 MB YUV420 | 71.8 | 72.6 |
| `bufferutil` | 1.382 MB YUV420 | 83.6 | 84.5 |

数据和可复跑页面在 `out/_t09b/wsbench.{html,mjs}`，60 帧、每帧等待同一个
ACK。`MV_WS_UNMASK=js node out/_t09b/wsbench.mjs 60` 是保留的 JS 基线；默认
为 `bufferutil`。服务器没有协商 `permessage-deflate`，所以没有压缩/解压缩
混入结果。

## 改动

- `package.json` / lockfile 增加 `bufferutil@4.1.0`；`export/wsframes.mjs`
  对每个掩码帧用其原生 `unmask()`，仍保留精确尺寸检查、顺序写入和 ACK。
- `src/engine/post.js` 增加仅导出使用的 R8、W×1.5H 帧缓冲和 GPU shader：输出
  BT.709 limited-range Y、2×2 平均的 U/V，并把三平面连续打包为 yuv420p。
  最后的既有 composite 仍画入默认 framebuffer，再 `blit` 到转换源，避免改变
  原有 final shader 的画面/色彩空间行为。
- `src/main.js` 在导出 URL 接受 `yuv`，把 readback buffer 和 WebSocket 帧大小
  切换为 RGBA 或 YUV420；YUV 关闭 PBO（默认本来就是关闭），现有缩略图和 PNG/raw
  RGBA 路径不变。
- `export/export.mjs` 在 `--yuv 1` 时为 FFmpeg 传入 `-pix_fmt yuv420p`，并跳过
  原有 `scale=...format=yuv420p`；`tools/export_parallel.mjs` 也透传该开关。
  `--raw-yuv 1 --raw FILE --yuv 1` 仅用于下述平面验证，普通 `--raw` 仍是 RGBA。

## 开关与推荐命令

```text
node tools/export_parallel.mjs --start 0 --end 395.4 --width 1280 --height 720 --fps 30 --jobs 4 --inflight 3 --yuv 1 --out out/film.mp4
```

- `--yuv 0`（默认）：原始 RGBA → FFmpeg scale/filter 路径。
- `--yuv 1`：GPU 打包 YUV420 → FFmpeg raw yuv420p 输入。
- `--inflight 3`：沿用 T09 已验证的稳定值；接收端按 ACK 释放，内存有上界。
- 建议继续使用 4 个 worker；T09 的稳定并行默认值未改变。YUV 减少每 worker 的
  浏览器→Node 负载，因此不建议把 `inflight` 加大来换取更多内存。

## 画质验证

五个要求时刻（5.0、20.5、44.0、60.0、126.0 秒）各取同一渲染帧：一份由 FFmpeg
的原 RGBA `scale=out_color_matrix=bt709:out_range=limited,format=yuv420p` 生成，
一份由新 GPU 打包器生成。两份 yuv420p 分别压为 CRF 1 MP4 后解码，比较 Y 平面：

| 时间（秒） | Y-PSNR（dB） |
| ---: | ---: |
| 5.0 | 58.70 |
| 20.5 | 59.27 |
| 44.0 | 62.33 |
| 60.0 | 58.21 |
| 126.0 | 56.36 |

均高于 50 dB。原始平面单帧（5.2 秒）复核为 Y=62.59 dB。验证 MP4、原始平面、
PSNR 日志和并排图位于 `out/_t09b/validation_*`；
`validation_5_side_by_side.png` 已人工目视检查。

默认 CRF 16 的两次独立完整导出不适合作为此转换阈值：即使输入相同，独立 H.264
码率控制的量化决策也会让解码帧只有约 38.6 dB。上述验证固定同一渲染帧并使用
CRF 1，以测量颜色转换而不是两次有损编码的差异；默认导出编码参数未改变。

## 速度

短段实际 smoke（5.0–5.5 秒、1280×720、单 worker、libx264 CRF 16、`inflight=3`）
如下。YUV 的 send 从 269.6 ms/frame 降至 228.8 ms/frame，端到端从 6.42 到
6.97 fps；readback 在本机仍是另一主要成本。

| 路径 | render ms | read ms | send ms | 帧循环 fps |
| --- | ---: | ---: | ---: | ---: |
| `--yuv 0` | 15.4 | 108.5 | 269.6 | 6.42 |
| `--yuv 1` | 12.2 | 113.8 | 228.8 | 6.97 |

已输出 0–14 秒、单路的 RGBA/YUV 文件到 `out/_t09b/bench_0_14_1j_*.mp4`。
完整“0–14 与 33–44、1/4 路、每项两次”的 NVENC 矩阵没有伪造结果：本机
`D:\Tools\ffmpeg\bin\ffmpeg.exe` 的 NVENC probe 明确失败（要求 API 13.1，驱动
只提供 13.0）；项目内置 `ffmpeg-static` 则无法启动。该限制与 T09 相同，故这里
不把 libx264 的数据标成 NVENC，也没有将不兼容的 FFmpeg 结果写入矩阵。
